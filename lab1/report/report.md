### 练习1：理解内核启动中的程序入口操作

>阅读 kern/init/entry.S内容代码，结合操作系统内核启动流程，说明指令 la sp, bootstacktop 完成了什么操作，目的是什么？ tail kern_init 完成了什么操作，目的是什么？

#### 问题一：`la sp, bootstacktop` 完成了什么操作，目的是什么？

相关代码位于 `kern/init/entry.S`：

```asm
kern_entry:
    la sp, bootstacktop

    tail kern_init

.section .data
    .align PGSHIFT
    .global bootstack
bootstack:
    .space KSTACKSIZE
    .global bootstacktop
bootstacktop:
```

`la` 是 RISC-V 汇编中的取地址伪指令，表示“load address”，用于把某个符号的地址装入寄存器。`sp` 是栈指针寄存器，对应寄存器 `x2`。

因此，`la sp, bootstacktop` 完成的操作是：

> 将内核启动栈的栈顶地址装入栈指针寄存器 `sp`。

内核栈空间由 `bootstack` 到 `bootstacktop` 之间的区域组成。其中，`bootstack` 是栈空间的起始位置，`.space KSTACKSIZE` 预留了内核栈所需的空间，`bootstacktop` 位于该空间的高地址端。

栈大小由 `kern/mm/memlayout.h` 和 `kern/mm/mmu.h` 中的定义决定：

```c
#define KSTACKPAGE          2
#define KSTACKSIZE          (KSTACKPAGE * PGSIZE)
```

```c
#define PGSIZE          4096
#define PGSHIFT         12
```

所以：

```text
KSTACKSIZE = 2 × 4096 = 8192 字节
```

也就是说，内核启动栈占两个页面，共 8 KB。RISC-V 的函数栈向低地址方向增长，因此一个空栈的栈指针应指向高地址端，也就是 `bootstacktop`。

这条指令的目的是：

> 为接下来执行 C 语言函数 `kern_init()` 建立合法的内核栈环境。

C 语言函数在运行过程中需要使用栈来保存局部变量、返回地址、被调用者保存寄存器以及函数调用过程中的临时数据。如果进入 `kern_init()` 前没有设置有效的栈指针，函数调用和局部变量访问就可能使用非法地址，导致内核无法正常启动。

另外，`bootstack` 通过 `.align PGSHIFT` 对齐到 4096 字节边界，栈大小 8192 字节也是页大小和对齐要求的整数倍，因此 `bootstacktop` 也满足 RISC-V 调用约定中的栈指针对齐要求。


#### 问题二：`tail kern_init` 完成了什么操作，目的是什么？

相关代码位于 `kern/init/entry.S`：

```asm
kern_entry:
    la sp, bootstacktop

    tail kern_init
```

以及 `kern/init/init.c`：

```c
int kern_init(void) __attribute__((noreturn));

int kern_init(void) {
    extern char edata[], end[];
    memset(edata, 0, end - edata);

    const char *message = "(THU.CST) os is loading ...\n";
    cprintf("%s\n\n", message);

    while (1)
        ;
}
```

`tail` 是 RISC-V 汇编中的尾调用伪指令。它会将程序控制权转移到目标函数，但不会像普通函数调用一样把返回地址保存到 `ra` 寄存器中。

在 RISC-V 中，`tail kern_init` 通常会被汇编器展开为类似于下面的指令：

```asm
auipc t1, %pcrel_hi(kern_init)
jalr  x0, %pcrel_lo(kern_init)(t1)
```

其中：

- `auipc` 用于计算 `kern_init` 相对于当前 PC 的地址。
- `jalr` 用于完成跳转。
- 目标寄存器是 `x0`，因此不会保存返回地址。

因此，`tail kern_init` 完成的操作是：

> 结束汇编入口 `kern_entry` 的控制流，将程序控制权转移到 C 语言函数 `kern_init()`。

这条指令的目的是：

> 完成从汇编启动代码到 C 语言内核入口的交接。

`kern_entry` 只负责建立内核栈并将控制权交给 C 语言代码。完成这两项工作后，汇编入口已经不需要继续执行，也不存在需要返回的位置。

此外，`kern_init()` 被声明为 `noreturn`，并且函数最后进入：

```c
while (1)
    ;
```

因此它不会正常返回。如果使用普通的函数调用指令，CPU 会把返回地址写入 `ra`，并在语义上表示“被调用函数返回后再继续执行”，但这在本实验中并不会发生。

所以这里使用 `tail` 而不是普通调用指令，既完成了入口跳转，也明确表达了“跳转后不返回”的执行逻辑。

结合前面的启动流程，两条指令的关系可以表示为：

```text
OpenSBI 将内核加载到 0x80200000
        ↓
跳转到 kern_entry
        ↓
la sp, bootstacktop
设置 8 KB 内核栈，sp 指向栈顶
        ↓
tail kern_init
进入 C 语言函数 kern_init()
        ↓
清理 .bss，输出启动信息，进入无限循环
```

#### 阶段一：CPU 从复位地址（0x1000）开始执行初始化固件（OpenSBI）的汇编代码，进行最基础的硬件初始化

首先执行`make debug`后通过`make gdb`进入调试：
![alt text](images\image-1.png)
可以发现连接后 PC 位于 `0x1000`，该地址是 `QEMU virt` 平台的复位入口

接着，输入指令`x/10i $pc`查看即将执行的十条汇编：
![alt text](images\stage1_reset_entry.png)


- **`0x1000: auipc t0,0x0`**

`auipc` 将立即数的高 20 位加到当前 PC 上。这里的立即数为 `0x0`，所以执行结果为：

```text
t0 = PC + (0x0 << 12)
   = 0x1000
```

执行后，`t0` 得到复位入口的基地址 `0x1000`，方便后续利用相对偏移访问附近的数据。

- **`0x1004: addi a1,t0,32`**

该指令将 `t0` 与十进制立即数 `32` 相加：

```text
a1 = 0x1000 + 32
   = 0x1000 + 0x20
   = 0x1020
```

在 RISC-V 启动约定中，`a1` 通常用于传递设备树等启动参数。执行后，`a1` 指向 `0x1020`。

- **`0x1008: csrr a0,mhartid`**

`csrr` 用于读取 RISC-V 的控制状态寄存器。这里读取的是 `mhartid`，即当前硬件线程 hart 的编号：

```text
a0 = mhartid
```

单核启动时通常得到 `a0 = 0`。该寄存器需要在机器模式 M-mode 下读取，而复位入口正运行在 M-mode。

- **`0x100c: ld t0,24(t0)`**

`ld` 表示从内存加载一个 64 位数据。访问地址为：

```text
0x1000 + 24 = 0x1018
```

因此该指令从 `0x1018` 读取 8 字节到 `t0`。该位置保存的跳转目标是：

```text
0x80000000
```

执行完成后：

```text
t0: 0x1000 -> 0x80000000
```

- **`0x1010: jr t0`**

`jr t0` 表示跳转到 `t0` 中保存的地址，其效果可以描述为：

```text
PC = t0
```

此时 `t0 = 0x80000000`，因此执行后：

```text
PC = 0x80000000
```

控制流由 QEMU 复位入口转入 OpenSBI 主体。

**说明复位入口真正执行的指令序列为：**

```text
0x1000  auipc t0,0x0
0x1004  addi  a1,t0,32
0x1008  csrr  a0,mhartid
0x100c  ld    t0,24(t0)
0x1010  jr    t0
```

这些指令完成了启动参数准备、hart ID 读取、跳转目标读取和控制权转移。执行完成后，PC 将从 `0x1000` 转移到 `0x80000000`，进入 OpenSBI 固件主体。

再进行单步调试，通过以下指令验证：


```gdb
si
info registers t0 a1 a0 pc
```
结果如图：
![](images\stage1_single_step.png)


单步执行结果与静态反汇编完全一致。阶段一由此可以确认：RISC-V 机器在 QEMU 中从 `0x1000` 开始执行，入口代码经过寄存器准备后跳转到 `0x80000000`。

#### 阶段二：SBI 固件进行主初始化，其核心任务之一是将内核加载到 0x80200000。可以使用watch *0x80200000观察内核加载瞬间，避免单步跟踪大量代码

到达地址`0x80000000`,我们查看该处的十条指令：
![](images\stage2_opensbi_entry.png)

- **`0x80000000: csrr a6,mhartid`**

`csrr` 用于读取控制状态寄存器 CSR。该指令从 `mhartid` 中读取当前硬件线程 hart 的编号，并把结果保存到通用寄存器 `a6`。

执行效果为：

```text
a6 = mhartid
```

当前在 hart 0 上启动，因此通常可以得到 `a6 = 0`。OpenSBI 使用 `a6` 作为临时寄存器保存 hart ID，为后面的主 hart 判断做准备。

- **`0x80000004: bgtz a6,0x80000108`**

`bgtz` 表示“大于零时分支”。如果 `a6 > 0`，则 PC 跳转到 `0x80000108`；否则继续执行下一条地址 `0x80000008`。

该指令用于区分主 hart 和其他 hart：

```text
if (mhartid > 0)
    PC = 0x80000108;
else
    PC = 0x80000008;
```

因此，hart 0 会继续执行 OpenSBI 的主初始化流程，非 0 号 hart 则转到 `0x80000108`，进入其对应的等待或次级启动路径。

- **`0x80000008: auipc t0,0x0`**

`auipc` 将当前指令地址 PC 与立即数高 20 位相加。这里的立即数为 `0x0`，因此：

```text
t0 = PC + (0x0 << 12)
   = 0x80000008
```

执行后，`t0` 得到当前指令地址 `0x80000008`，作为后续相对地址计算的基准。

- **`0x8000000c: addi t0,t0,1032`**

该指令完成低 12 位偏移补偿。立即数 `1032` 是十进制数，等于十六进制 `0x408`：

```text
t0 = 0x80000008 + 0x408
   = 0x80000410
```

执行后，`t0` 从当前代码位置变为 OpenSBI 内部数据地址 `0x80000410`。由于该区域没有对应内核符号，GDB 只能显示数值地址。

- **`0x80000010: auipc t1,0x0`**

再次以当前 PC 为基准计算地址：

```text
t1 = 0x80000010 + 0
   = 0x80000010
```

此时 `t1` 暂时保存当前指令的地址，下一步通过 `addi` 将其调整到 OpenSBI 固件入口。

- **`0x80000014: addi t1,t1,-16`**

立即数 `-16` 等于 `-0x10`：

```text
t1 = 0x80000010 - 0x10
   = 0x80000000
```

因此 `t1` 保存的是 OpenSBI 固件入口地址 `0x80000000`。这一组 `auipc + addi` 指令以位置无关的方式计算出了固件起始地址。

- **`0x80000018: sd t1,0(t0)`**

`sd` 表示存储一个 64 位数据。该指令把 `t1` 中的 OpenSBI 入口地址写入 `t0` 指向的内存地址：

```text
memory[0x80000410] = t1
memory[0x80000410] = 0x80000000
```

这说明 OpenSBI 在进入后续初始化前，会把固件入口地址保存到内部数据区，供重定位或其他启动流程使用。具体变量名无法显示，是因为 GDB 当前只加载了 `bin/kernel` 的符号，没有加载 OpenSBI 的完整符号表。

- **`0x8000001c: auipc t0,0x0`**

重新以当前 PC 为基准计算地址：

```text
t0 = 0x8000001c + 0
   = 0x8000001c
```

这里再次使用 `auipc`，说明后续还要访问 OpenSBI 附近的另一个内部数据位置。

- **`0x80000020: addi t0,t0,1020`**

立即数 `1020` 等于 `0x3fc`：

```text
t0 = 0x8000001c + 0x3fc
   = 0x80000418
```

执行后，`t0` 指向 `0x80000418`，这是 OpenSBI 内部的另一个启动数据槽。

- **`0x80000024: ld t0,0(t0)`**

`ld` 从内存读取一个 64 位数据。该指令从 `t0` 指向的 `0x80000418` 读取内容，并覆盖写回 `t0`：

```text
t0 = memory[0x80000418]
```
这组入口指令完成了以下工作：

1. 读取当前 hart ID；
2. 判断当前 hart 是否为主 hart；
3. 让非 0 号 hart 进入其他启动路径；
4. 通过 `auipc + addi` 计算相对当前 PC 的绝对地址；
5. 将 OpenSBI 入口地址 `0x80000000` 保存到内部数据区；
6. 从内部数据槽读取后续启动需要使用的值。

当前实验的启动路径可以表示为：

```text
复位入口 0x1000
        ↓
OpenSBI 主体 0x80000000
        ↓
OpenSBI 初始化和重定位
        ↓
内核入口 0x80200000
```






#### 阶段三：SBI 最后跳转到 0x80200000，将控制权移交内核。使用 b *0x80200000 可在此中断，验证内核开始执行

通过指令令`break *0x80200000`在被加载的内核镜像位置打上断点，并运行到对应位置：
![](images\stage3_kernel_entry_breakpoint.png)
之后查看此处的10条指令:
![](images\stage3_kernel_entry_disassembly.png)

从截图可以看到，断点命中后 GDB 停在 `kern/init/entry.S` 第 7 行，当前 PC 为 `0x80200000`。对该位置执行 `x/10i $pc` 后，可以观察到从 `kern_entry` 到 `kern_init` 开始执行的连续指令。

- **`0x80200000 <kern_entry>: auipc sp,0x3`**

当前 PC 为 `0x80200000`，`auipc` 加上立即数高 20 位：

```text
sp = 0x80200000 + (0x3 << 12)
   = 0x80200000 + 0x3000
   = 0x80203000
```

`0x80203000` 是链接后的 `bootstacktop` 地址。该指令对应 `entry.S` 中的 `la sp, bootstacktop`，作用是开始建立内核启动栈。

- **`0x80200004 <kern_entry+4>: mv sp,sp`**

`mv sp,sp` 显示为寄存器之间的数据传送，它实际编码为：

```asm
addi sp,sp,0
```

这是 `la sp, bootstacktop` 伪指令展开后的低位补偿部分。由于 `bootstacktop = 0x80203000` 的低 12 位为 0，所以这里加上的偏移量也是 0。两条指令执行完成后，`sp = 0x80203000`，内核启动栈建立完成。

- **`0x80200008 <kern_entry+8>: j 0x8020000a <kern_init>`**

该指令对应汇编入口中的：

```asm
tail kern_init
```

它无条件跳转到 C 语言函数 `kern_init`，不需要保存返回地址。GDB 已经通过内核符号表把目标标记为 `<kern_init>`。

跳转目标是 `0x8020000a`，而不是旧报告中的 `0x8020000c`，原因是当前工具链启用了 RVC 压缩指令扩展：

```text
0x80200008 + 2 = 0x8020000a
```

`0x80200008` 处的压缩跳转 `j` 只占 2 字节，因此下一条指令从 `0x8020000a` 开始。如果使用不支持 RVC 或没有启用压缩指令的旧工具链，同一跳转可能占 4 字节，目标地址就会表现为 `0x8020000c`。

- **`0x8020000a <kern_init>: auipc a0,0x3`**

该指令开始计算 `kern_init` 中第一个数据地址：

```text
a0 = 0x8020000a + 0x3000
   = 0x8020300a
```

这个结果还不是最终地址，下一条 `addi` 会继续补偿低 12 位。

- **`0x8020000e <kern_init+4>: addi a0,a0,-2`**

```text
a0 = 0x8020300a - 0x2
   = 0x80203008
```

根据内核符号表，`0x80203008` 对应 `edata`，因此这两条指令实际上在计算 `extern char edata[]` 的地址。

- **`0x80200012 <kern_init+8>: auipc a2,0x3`**

该指令开始计算另一个数据地址：

```text
a2 = 0x80200012 + 0x3000
   = 0x80203012
```

- **`0x80200016 <kern_init+12>: addi a2,a2,-10`**

立即数 `-10` 等于 `-0xa`：

```text
a2 = 0x80203012 - 0xa
   = 0x80203008
```

根据内核符号表，`0x80203008` 同时对应 `edata` 和 `end`。因此当前链接结果中两者的地址相同。

- **`0x8020001a <kern_init+16>: addi sp,sp,-16`**

该指令在启动栈上向低地址移动 16 字节，为函数调用准备栈帧：

```text
sp = 0x80203000 - 0x10
   = 0x80202ff0
```

RISC-V 的栈向低地址方向增长，因此减小 `sp` 等价于分配栈空间。

- **`0x8020001c <kern_init+18>: li a1,0`**

`li` 是加载立即数的伪指令，这里将 `a1` 设置为 0：

```text
a1 = 0
```

该寄存器会作为后续 `memset(edata, 0, end - edata)` 的填充值。

- **`0x8020001e <kern_init+20>: sub a2,a2,a0`**

该指令计算清零区间长度：

```text
a2 = a2 - a0
   = end - edata
   = 0x80203008 - 0x80203008
   = 0
```

因此当前链接结果对应的清零长度为 0。


该过程验证了 OpenSBI 已经把控制权交给内核入口 `0x80200000`。内核首先通过 `auipc` 和 `addi` 设置启动栈 `bootstacktop`，随后跳转到 `kern_init`。进入 `kern_init` 后，程序继续计算 `edata` 和 `end`，为调用 `memset` 准备参数，并建立函数栈帧。

## 四、实验总结与收获

### 1. 本实验的重要知识点及其与 OS 原理的对应关系

本实验的逻辑主线可以概括为：

```text
QEMU 加电复位 0x1000
        ↓
复位代码跳转到 OpenSBI 0x80000000
        ↓
OpenSBI 完成 M 态初始化和内核加载
        ↓
内核入口 kern_entry 0x80200000
        ↓
entry.S 建立内核启动栈
        ↓
tail kern_init，从汇编入口转入 C 语言内核
        ↓
清理 .bss、输出启动信息、进入无限循环
```

这条主线说明，一个最小的操作系统内核至少需要完成“获得控制权、建立 C 语言执行环境、初始化自身数据、提供最基本的输出手段”这几项工作。下面分别说明实验中的知识点及其对应的 OS 原理。

#### （1）加电复位、固件和引导加载：从 `0x1000` 到 `0x80200000`

实验中的体现：QEMU 模拟的 RISC-V 处理器上电后，PC 被设置为复位地址 `0x1000`。复位代码先完成最基本的硬件和环境准备，然后跳转到 `0x80000000` 处的 OpenSBI。OpenSBI 运行在 M 态，负责固件层面的初始化和启动下一阶段软件，最终把控制权交给位于 `0x80200000` 的内核入口 `kern_entry`。

对应的 OS 原理：操作系统的引导过程通常不能由操作系统自己完成，而必须依靠固件和 bootloader 逐层接力。现代 PC 中通常是 UEFI/BIOS 先初始化硬件，再把控制权交给 GRUB 或 Windows Boot Manager 等引导程序，最后由引导程序加载操作系统内核。



#### （2）RISC-V 特权级、OpenSBI 与 `ecall`

实验中的体现：OpenSBI 作为固件运行在 M 态，内核按照 RISC-V 启动约定运行在 S 态，U 态在本实验中尚未使用。内核需要输出字符时，并不是直接操作真实硬件，而是通过 `ecall` 请求 OpenSBI 提供控制台服务。`sbi_call` 将 SBI 服务编号放入 `x17`，把参数放入 `x10` 至 `x12`，执行 `ecall` 后从 `x10` 取得返回值。

对应的 OS 原理：现代处理器通过多个特权级实现硬件保护和职责隔离。用户程序运行在低特权级，操作系统内核运行在高特权级；用户程序需要访问硬件或执行特权操作时，必须通过系统调用陷入内核，由内核进行参数检查和资源管理。


#### （3）链接脚本、程序段布局与地址相关性

实验中的体现：`tools/kernel.ld` 将内核基地址设置为 `0x80200000`，并通过 `ENTRY(kern_entry)` 指定入口。链接脚本按照 `.text`、`.rodata`、`.data`、`.sdata`、`.bss` 的顺序组织内核，并用 `edata` 和 `end` 标记初始化数据区和 `.bss` 区的结束位置。内核的第一条指令必须位于 `0x80200000`，否则 OpenSBI 跳转后将无法执行正确的代码。

对应的 OS 原理：操作系统和普通程序的可执行文件都需要明确的地址空间与段布局。代码段存放指令，只读数据段存放常量，数据段存放已初始化的全局变量，`.bss` 段保存需要清零的未初始化全局变量。链接器和加载器共同决定这些内容最终放在何处。



#### （4）交叉编译、ELF 与二进制镜像

实验中的体现：实验使用 `riscv64-unknown-elf-gcc` 编译 C 和汇编源码，使用 `ld` 按链接脚本生成 ELF 格式的 `bin/kernel`，再用 `objcopy` 去掉符号和调试信息，生成二进制镜像 `bin/ucore.img`。`make` 和 `Makefile` 自动管理编译、链接和镜像生成过程。

对应的 OS 原理：操作系统开发通常采用交叉编译，因为开发机与目标机的指令集和运行环境不同。ELF 文件保存段信息、符号表和重定位信息，便于链接和调试；bootloader 或加载器最终需要的是可以直接放到内存中执行的镜像。


#### （5）内核启动栈、RISC-V 调用约定与汇编到 C 的交接

实验中的体现：`kern/init/entry.S` 中的 `la sp, bootstacktop` 把内核启动栈的栈顶地址装入 `sp`。内核栈由 `bootstack` 向后预留 `KSTACKSIZE` 大小，本实验中为两个页面，即 8 KB。RISC-V 栈向低地址增长，因此使用高地址端的 `bootstacktop` 作为初始栈顶。随后 `tail kern_init` 不保存返回地址，直接把控制权交给 C 函数 `kern_init`；`kern_init` 又通过 `noreturn` 声明和无限循环表明它不会返回。

对应的 OS 原理：栈是函数调用、局部变量、返回地址和寄存器保存的基础。进入 C 语言代码前必须建立符合调用约定的栈，否则函数调用和局部变量访问会失败。`ra`、`sp`、参数寄存器 `a0` 至 `a7`、返回值寄存器 `a0` 等共同构成了 RISC-V 的函数调用环境。



#### （6）内核初始化与 `.bss` 清零

实验中的体现：`kern_init` 首先声明链接器提供的 `edata` 和 `end` 符号，然后调用：

```c
memset(edata, 0, end - edata);
```

这条语句的作用是把从 `edata` 到 `end` 的 `.bss` 区域清零。本次链接结果中 `edata` 和 `end` 都等于 `0x80203008`，所以实际清零长度为 0；如果内核中存在未初始化或需要零初始化的全局数据，该区域就会包含相应字节并被清零。之后内核输出 `(THU.CST) os is loading ...`，最后执行 `while (1);`。

对应的 OS 原理：C 语言要求具有静态存储期的未初始化对象在程序开始执行时表现为零值。为了减小可执行文件体积，这类对象通常放在 `.bss` 段中，文件中只记录段的地址和大小，由加载器或启动代码在运行时清零。内核启动阶段完成这部分初始化，才能保证后续 C 代码使用的全局变量具有正确初值。



#### （7）格式化输出、SBI 服务与分层 I/O

实验中的体现：内核调用 `cprintf("%s\n\n", message)` 输出启动信息。调用链可以概括为：

```text
cprintf
    ↓
vcprintf
    ↓
vprintfmt
    ↓
cons_putc
    ↓
sbi_console_putchar
    ↓
ecall 请求 OpenSBI 输出字符
```

其中，`cprintf` 负责处理可变参数和格式化，`cons_putc` 提供控制台设备抽象，`sbi_console_putchar` 则把字符输出请求交给运行在 M 态的 OpenSBI。内核不需要了解 QEMU 控制台设备的寄存器细节，只需使用统一的 SBI 接口。

对应的 OS 原理：操作系统需要通过设备抽象层和驱动程序管理外设。高层函数只关心“输出一个字符或一段格式化文本”，底层驱动负责具体的设备访问；系统调用则负责在用户态和内核态之间建立受控接口。


#### （8）QEMU 与 GDB 的远程调试方法

实验中的体现：`make debug` 通过 `-S -s` 让 QEMU 启动后暂停，并监听 GDB 的远程调试端口；`make gdb` 将 `bin/kernel` 的符号表加载到 GDB，然后连接 QEMU。实验中使用了 `x/10i $pc` 查看指令、`si` 单步执行、`info registers` 查看寄存器和 PC、`disassemble kern_init` 查看反汇编，以及在 `0x80200000` 和 `kern_init` 处设置断点。通过这些操作，实际观察到了从 OpenSBI 到 `kern_entry`，再进入 `kern_init` 的控制流。

对应的 OS 原理：调试器通过符号、地址、断点和寄存器状态观察程序执行。对于操作系统内核，GDB 通常通过 QEMU 等模拟器或硬件调试接口连接目标机，进行远程调试。地址、符号表、调用栈和寄存器现场是理解内核执行状态的基础。


### 2. OS 原理中很重要、但在本实验中没有对应上的知识点



#### （1）U 态用户程序、系统调用与用户态保护

指导书在介绍 RISC-V 特权级时明确给出了 U、S、M 三种模式：U 态用于用户程序，S 态用于操作系统内核，M 态用于固件；同时说明 U 态执行 `ecall` 会陷入 S 态，这是系统调用的底层机制。在本实验中，内核运行在 S 态，OpenSBI 运行在 M 态，已经体现了 S 态向 M 态请求服务的 `ecall`，但没有加载或运行任何 U 态用户程序。

因此，指导书中提到的“用户程序通过系统调用进入内核”虽然属于重要 OS 原理，却没有在实验中对应实现。当前内核没有 U 态到 S 态的陷入与返回、系统调用编号分派、参数检查、用户地址合法性检查，也没有通过页表隔离用户地址空间和内核地址空间。实验中的 `ecall` 是内核向 OpenSBI 请求控制台服务，不能等同于用户程序向操作系统发起的系统调用。






#### （2）物理内存管理与虚拟内存

指导书在介绍程序内存布局时明确列出了 `.text`、`.rodata`、`.data`、`.bss`、栈和堆，并在项目组成中列出了 `kern/mm/memlayout.h`、`mmu.h`、`pmm.c` 和 `pmm.h`，同时说明内存管理相关内容将在后续实验中完善。本实验对应实现的只是链接脚本确定内存布局、建立一个 8 KB 内核启动栈，以及调用 `memset(edata, 0, end - edata)` 清理 `.bss` 区域。

指导书中提到的堆和后续内存管理机制，在当前内核中还没有对应实现。内核被固定在 `0x80200000` 启动，当前使用的地址都是链接后的固定地址，没有建立页表，也没有虚拟地址到物理地址的转换。因此，物理页面探测、页框分配与回收、动态堆分配、页表、TLB、缺页异常、按需分页、页面置换和地址空间隔离等由指导书引出或留待后续实现的内容，都不属于 Lab 1 的实际功能。
